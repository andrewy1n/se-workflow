## Problem

The dashboard is only useful when it is one keystroke away in the tmux session, and it must find the right store for the repo in the current pane.

## Approach

1. dashboard-launcher (se-workflow `scripts/dashboard` plus `scripts/tmux-dashboard.conf`): resolve the store for a directory (git toplevel; `~/.artifacts/<repo>` if it has meta.json, else `<toplevel>/.artifacts`), resolve the runtime binary (`$ADAPTIVE_ARTIFACTS_BIN`, else `~/adaptive-artifacts/bin/adaptive-artifacts`, else `adaptive-artifacts` on PATH), and exec `watch --id project:dashboard`. If there is no store, or the store's contract has no dashboard view, print why and wait for a key so a popup does not flash shut. The conf snippet binds prefix + A to a popup and prefix + S to a side pane, both in `#{pane_current_path}`.
2. dashboard-status-segment (se-workflow `scripts/dashboard-status`): read the Claude Code status JSON on stdin (or a directory argument), resolve the store the same way, and print one line such as `watch-dashboard · 1 running · 2 ready · 1 needs you`, or nothing when there is no store. It must return within 1 s.
3. verify-tmux-integration-phase (depends on 1 and 2): integration test on an isolated tmux server.
4. README section: install the snippet and the status segment.

## Exit criteria

- The side-pane binding shows the dashboard for the pane's repo: verified by an isolated tmux server test that runs the bound command and checks `capture-pane`.
- The popup binding runs the same launcher in the pane's directory: verified by the same test reading `list-keys` and running the popup's command in a pane.
- The status segment prints the right counts within 1 s: verified by the same test against a seeded store.
- Both full suites pass: verified by running them.
