## Problem

Verification tasks take 20 to 80 minutes. Each one runs the phase's own checks and then the full suite, which repeats the same dashboard pilot tests. A failure is fixed inside the verification task and the suite is run again. The parent often runs those commands a second time. One serial run of the dashboard app and requirement pilots is 506 seconds. One full non-tmux suite is about 4 minutes and still growing, plus a serial tmux leg of about 90 seconds.

## Approach

Decisions: phase-checks-only, verify-stop. Run as structured work: specification `verify-budget`, design `verify-budget`.

A verification task runs that phase's integration check through the real entry point and the tests the phase's exit criteria name. It does not run the full suite, and it does not run `tests/test_dashboard_app.py` without a `-k` filter for this phase. `AGENTS.md` and `CLAUDE.md` tell a task to run its own `verify_command` at close.

When a check fails, the executor returns fail and does not edit the tree. `verify-work` leaves the work-item `in_progress` and the assessment uses `next` `execute`.

Planned full-suite acceptances on `verify-spec-view`, `verify-evidence-matrix`, and `verify-journal-view` are superseded with the phase-scoped command before those tasks dispatch.

## Exit criteria

`tests/test_verify_budget.py` fails if `plan-phase`, `execute-phase`, `verify-work`, `AGENTS.md`, or `CLAUDE.md` tells verification or task close to run the full suite, and it fails if `execute-phase` omits the no-edit fail return. `tests/test_skill_contract_consistency.py` passes.

Active acceptances for `verify-spec-view`, `verify-evidence-matrix`, and `verify-journal-view` do not name the full suite, checked by reading those records.

The next verification task's in-progress to done span is at most 10 minutes, checked from the work-item log.
