## Problem

The loop records a goal, a phase approach, tasks, and a pass/fail check. Specification, semantic integration, evidence that is neither pass nor fail, a bounded repair loop, and release or feedback have no records. Later stages rebuild them from prose. Git merge is treated as integration, and a passing test is treated as done.

## Approach

Decision: lifecycle-records.

Keep `engage`, `init`, `discuss`, `plan-phase`, `execute-phase`, and `verify-work`. Add four record types on patterns the runtime already has, and grade `check-run` results. Do not add a skill per stage.

- `specification` (definition), one per phase, `weight` `light` or `full`. Light is a short required behavior and success statement. Full also records constraints and out of scope. `acceptance` gains an optional reference to that specification. Existing acceptance records stay valid with no reference.
- Design stays `decision`, `constraint`, and the phase Approach. `discuss` remains the design stage and stays skippable when the user already fixed the approach or the change has no architectural choice.
- Diagnosis stays `finding`. The failure itself stays `investigation-observation`. No diagnosis type.
- `integration-report` (observation) on the phase, written after parallel execution and before the verification task. `result` is `pass`, `fail`, or `blocked`. A clean git merge does not write `pass` by itself. A `fail` or `blocked` result goes to diagnose and repair, then back through integrate and verify.
- `check-run.result` is `pass`, `fail`, `blocked`, or `insufficient`. `insufficient` means the criterion was not shown, including when other tests passed. `pass` is evidence for that criterion only.
- Repair counts failed attempts for the work-item. At three failed repairs, or when the diagnosis is unresolved, open a blocking continuity-question and a finding with `needs` `human`.
- `release` (current-status) is optional. States: `ready`, `merged`, `artifact`, `deploying`, `deployed`, `failed`. Landing may record `merged`. Nothing in this phase deploys.
- `feedback` (observation) is a signal `engage` can classify as new work. Nothing in this phase collects it.

Incidental work and a `light` specification skip `integration-report` and `release`. Incidental work skips `specification` too.

Traceability is payload references plus the existing `informed_by` link from check-run to acceptance: specification, acceptance, decision, work-item, integration-report, check-run.

This phase changes `contract/project-design.json`, the six skills, the README, and tests. It refreshes this repo's live design when those types land. It does not add a deployer, a monitor, or a dashboard for the new types.

## Exit criteria

- The bundled contract declares `specification`, `integration-report`, `release`, and `feedback` on existing patterns, and `check-run` allows `pass`, `fail`, `blocked`, and `insufficient`. `uv run --with textual --with pytest python -m pytest tests/test_contract_self_consistency.py -q` passes.
- The six skills document only contract-legal writes for those types, including the light and incidental skips. `uv run --with textual --with pytest python -m pytest tests/test_skill_contract_consistency.py -q` passes.
- Skill tests cover a pass path through specify, design, plan, execute, integrate, verify, and release; a fail path through diagnose, repair, and verify pass; a third repair failure that escalates; and parallel tasks whose integration-report is `fail` until reconciliation. The test module is named at plan-phase. That module passes.
- The README describes the stages the skills actually write, and describes release and feedback as records with no deployer or collector. The phase verification task checks the README against the skills.
