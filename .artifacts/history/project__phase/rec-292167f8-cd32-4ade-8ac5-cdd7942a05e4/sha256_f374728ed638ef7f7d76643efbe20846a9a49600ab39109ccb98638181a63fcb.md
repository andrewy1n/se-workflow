## Problem

The loop records a goal, a phase approach, tasks, and a pass/fail check. A passing test is treated as done, and a failure is treated as a coding problem. Specification, design, semantic integration, per-requirement evidence, and the choice of which stage to revisit have no records.

## Approach

Decisions: lifecycle-records, two-modes, evidence-escalation, release-ready.

Keep `engage`, `init`, `discuss`, `plan-phase`, `execute-phase`, and `verify-work`. Do not add a skill per stage.

Two modes are the rule. Structured work is a phase that has a specification: specify, design, plan, execute, integrate when an implementation wave is parallel, verify, assess, and release `ready` when every requirement is verified. Simple work is incidental, or a phase with no specification: execute, then verify as pass or fail. Simple work does not write specification, design, integration-report, assessment, or release.

- `discuss` writes one `specification` (what must be true) and one `design` (how it should work), then the decisions a later reader would re-open. Requirements use stable ids `R1`, `R2`, …. `weight` is `light` or `full`. Simple work skips both records.
- `plan-phase` stamps each work-item with `requirements` and `decisions`, and each acceptance with `requirement`, when a specification exists. Dependencies and waves stay derived.
- `execute-phase` hands the executor the named requirements, design invariants, and decisions. After a parallel implementation wave, and before the verification task, it writes an `integration-report`. A clean git merge does not make that report `pass`.
- Verify and assess stay separate. A `check-run` records what happened: `result` `pass`, `fail`, `blocked`, or `insufficient`, plus `requirement` and `evidence_kind` when the acceptance names a requirement. It does not set `level` or `next`. An `assessment` reads those check-runs and decides what the evidence means for the requirement: `status` `verified`, `failed`, `insufficient`, or `blocked`; `level`; `next` of `specify`, `design`, `plan`, `execute`, `integrate`, `verify`, or `release`.
- The first diagnosis follows the evidence. Implementation returns to execute. Design returns to design. A missing task returns to plan. An ambiguous or contradicted requirement returns to specify. An integration-report `fail` returns to execute when a task must change, otherwise to integrate. Insufficient evidence returns to verify. `environment` or `unknown` asks the user.
- Escalation follows evidence-escalation. A later assessment for the same requirement stays at the same level only when the new check-runs add evidence or the previous cause is resolved. Otherwise it raises one step on the ladder `implementation` → `design` → `specification`, and says why. `plan` and `integration` are direct diagnoses, not rungs on that ladder. At `specification`, with still no new evidence, ask the user.
- Release follows release-ready. When every assessment is `verified`, write `release` state `ready`. `ready` means the evidence is sufficient. It does not mean merged or deployed. Landing may later record `merged`. This phase writes `ready` only.
- `feedback` is a signal `engage` can route into specify. Nothing collects it.

Traceability is payload fields plus the existing `informed_by` link: requirement id, decision subject, work-item, check-run, assessment.
