## Problem

The dashboard is organized by effort, and phases are only group headers inside the task table. There is no way to select a phase. Reaching another phase means moving the cursor to its header, unfolding `N earlier phases done`, and pressing Enter or `p`. The stepper looks like a phase picker but only expands finished titles, and it shows only the first in-progress phase when several run in parallel. Status tabs, counts, and progress cover the whole effort, so finished tasks crowd out the active ones. The Spec, Evidence, and Journal views planned for later phases are per phase and need a selected phase.

## Approach

Decisions: phase-selection-scope, phase-selector-keys, phase-sections, quiet-header, selection-follow, parallel-phase-default, wave-strip, finished-effort-toggle, activity-merge, ux-phase-split.

This phase is the first of five UX phases (phase-selector, human-gates, spec-view, evidence-matrix, journal-view). It keeps the dashboard read-only and does not change `contract/project-design.json` or `~/adaptive-artifacts`.

Waves (all inline except verification):

1. `phase-model-selection` — add selection state and helpers to `dashboard/model.py`: default phase from most-recent activity, fallbacks, follow/pin semantics, no-phase handling, and merged activity lines. Cover with `tests/test_dashboard_model.py`.
2. `phase-table-scope` — update `dashboard/tasks.py` to scope counts, task rows, and progress to a selected phase while preserving the grouped All-phases table and removing the wave column. Cover with `tests/test_dashboard_tasks.py`.
3. `phase-selector-ui` — replace the stepper with the selector in `dashboard/app.py`, add `[`, `]`, `P`, click, picker, wave strip, `p`, `f`, `?`, and finished-effort toggle. Cover with `tests/test_dashboard_app.py`.
4. `phase-once-render` — update `render_once` so `dashboard/bin/dashboard --once` prints the selector line and wave strip. Cover with `tests/test_dashboard_integration.py`.
5. `verify-phase-selector` — subagent runs the integration check and full suite.

Collision notes: `dashboard/app.py` and `dashboard/tasks.py` are edited by multiple tasks; model changes must land before UI tasks use the new helpers. All four code tasks share the same test fixtures.

## Exit criteria

- Default selection, scoped counts, follow and pin, wave strip text, merged activity, and finished-effort hiding hold against seeded stores (model and task tests in `tests/test_dashboard_model.py` and `tests/test_dashboard_tasks.py`).
- `[`, `]`, `P`, clicks, `p`, `f`, and `?` behave as specified in a Textual pilot (`tests/test_dashboard_app.py`).
- `dashboard/bin/dashboard --once` prints the selector line and wave strip at the default selection (`tests/test_dashboard_integration.py`).
- The full suite passes.
