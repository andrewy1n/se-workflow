## Description

Prove the loop records and routes on a fresh store through the real CLI.

## Approach

Add `tests/test_evidence_loop.py`. Follow `tests/test_contract_self_consistency.py`: subprocess the `adaptive-artifacts` CLI against a fresh git store built from `contract/project-design.json`. Do not import the runtime.

Cover these cases:

- Happy path. Create a specification with `R1`, a design, a work-item whose `requirements` is `R1`, an acceptance whose `requirement` is `R1`, a passing check-run with `evidence_kind`, an assessment `status` `verified` `next` `release` `confidence` `high`, and a release `state` `ready`.
- Implementation failure. A failed check-run and an assessment `level` `implementation` `next` `execute`. The work-item stays `in_progress`.
- Design failure. An assessment `level` `design` `next` `design`, with no transition of the work-item to `done`.
- Persistent failure. Three failed assessments for one requirement (supersede the current-status twice). The third case is the skill rule: the test asserts `skills/verify-work/SKILL.md` refuses a fourth `next` `execute` and opens a blocking continuity-question. Also create that question through the CLI and show it is `open`.
- Parallel integration. An integration-report `result` `fail` is a legal record, and a later report can be `pass` only as a new record (observation, not an in-place edit of the fail).
- Insufficient evidence. An assessment `status` `insufficient` `level` `verification` `next` `verify` with `missing` naming the absent check. A passing check-run for a different kind does not force `status` `verified`.
- Backward compatibility. A check-run whose `result` is `pass` and that omits `requirement` and `evidence_kind` still creates.

Assert `validate` accepts the store after each scenario.
