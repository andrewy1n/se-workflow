## Interfaces

The contract types the skills write are the types the tests drive. discuss writes specification and design only for structured work. plan-phase stamps requirements, decisions, and requirement only when a specification exists. execute-phase writes integration-report with result pass, fail, or blocked. verify-work writes check-runs with no level or next, then assessment status, level, and next, then release state ready. engage lists project:feedback and does not create it. README Lifecycle states those same writes. test_evidence_loop.py creates them through the CLI. File ownership does not overlap: contract and ensure-store, discuss and init, plan-phase, execute-phase, verify-work and engage, README and test_readme_lifecycle.py, and test_evidence_loop.py.

## Assumptions

Simple work omits specification, design, assessment, and release. Structured work uses stable requirement ids. check-run.result stays a free field because a recorded check-run uses result tdd. evidence_kind, assessment status, level, next, confidence, and integration-report result stay enums. A clean git merge is not integration success.

## Invariants

A failing check-run does not carry level or next and does not itself choose the next stage. Repeated implementation failure with no new evidence raises to design. plan and integration are direct diagnoses. Release ready means every requirement is verified, not merged or deployed. Incidental work and a phase with no specification stay on execute then verify.
