## Architecture

Add `project:backlog-item` beside `project:feedback` in the bundled contract. Pattern is `current-status` (not observation): lifecycle active/superseded so status can change via supersede. Payload requires `effort` and `status` (`open` | `promoted` | `dismissed`); `source` and `phase` are optional (`phase` set when promoted). The item body holds the parked description (and an external URL when useful).

Status changes use `supersede` of the active record with the new `status` (and `phase` on promote). Open items are those with lifecycle `active` and `payload.status` `open`. Dismissed and promoted successors stay in history; they are not listed as open backlog.

`project:feedback` stays an observation and is untouched: engage still lists it and routes into discuss; nothing collects it; it is not a backlog.

Handoff gains a role for open backlog items, grouped by `effort`, selecting `lifecycle_state` active and `payload.status` equals `open`. Skills (`engage`, `ensure-store`, README) document create, list, promote, and dismiss.

## Interfaces

Create (park):

```bash
adaptive-artifacts create --type project:backlog-item \
  --subject "<item-slug>" \
  --payload '{"effort":"<effort-slug>","status":"open","source":"<optional>"}' \
  --body-file "<description.md>"
```

List open for a focus:

```bash
adaptive-artifacts list --type project:backlog-item \
  --where payload.effort=<focus> --where payload.status=open --state active
```

Promote (structured → discuss / new phase; simple → incidental work-item), then supersede:

```bash
adaptive-artifacts supersede --type project:backlog-item --id <id> \
  --expected-revision <revision> \
  --payload '{"status":"promoted","phase":"<phase-slug-or-empty>","effort":"<effort-slug>"}'
```

Dismiss:

```bash
adaptive-artifacts supersede --type project:backlog-item --id <id> \
  --expected-revision <revision> \
  --payload '{"status":"dismissed","effort":"<effort-slug>"}'
```

Engage: after naming focus, list open backlog for that effort; when the user parks work, offer create; when they pick an item to start, promote and route like new phase discuss (or incidental). Do not scrape GitHub. Do not create `project:feedback` for parking.

## Decisions

- backlog-vs-feedback: new `backlog-item`; keep `feedback`
- backlog-effort-scope: `effort` required
- backlog-promote: close via supersede and route to discuss/new phase or incidental work-item
- backlog-capture: parent/session CLI capture; no collector
- backlog-item-pattern: `current-status` with supersede (not observation)

## Invariants

- Feedback never stores deferred backlog.
- Structured promote never skips discuss for a new phase.
- Every backlog-item has an effort subject that names a goal area.
- Only `status=open` active items appear as live backlog in handoff and default lists.

## Assumptions

- `current-status` records supersede the same way assessment and goals do.
- Existing ensure-store currency checks can add `backlog-item` next to `feedback`.
- No adaptive-artifacts runtime change is required if the contract expresses the type and view role.

## Tradeoffs

- Extra record type instead of widening feedback: clearer engage rules; slightly larger contract.
- `current-status` instead of observation: legal promote/dismiss; not in the same occurrence family as feedback.
- Effort required: no parking before a goal exists; avoids orphan index.
- Promote through discuss: slower clear of backlog; preserves specify/design for structured work.
- Explicit capture: double-entry vs GitHub possible; store remains authority.

## Risks

- Handoff role selection must use `equals open` (not `not_equals` closed) so missing status never looks open.
- Decision subject `backlog-capture` shares the phase slug; readers must disambiguate by record type.
- Shell wrappers that redirect `--store` away from the worktree `.artifacts` can hide backlog writes; skills should keep documenting the project store.
