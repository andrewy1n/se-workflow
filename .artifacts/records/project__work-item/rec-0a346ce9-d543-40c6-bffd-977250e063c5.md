## Description

Document the loop the skills actually implement.

## Approach

Add a lifecycle section to `README.md`. State decision two-modes as the rule: structured work (a phase with a specification) runs specify, design, plan, execute, integrate when a wave is parallel, verify, assess, and release `ready`; simple work (incidental, or a phase with no specification) runs execute, then verify as pass or fail.

State the verify/assess split. A check-run records what happened and which requirement it bears on. An assessment records what that evidence means and which stage is next. A failing test does not itself choose the stage.

Describe the routes: implementation to execute, design to design, plan to plan, specification to specify, integration to integrate or execute, insufficient evidence to verify. Describe evidence-escalation: the same level repeats only when evidence increased or the cause was resolved; otherwise the ladder is implementation, then design, then specification. `plan` and `integration` are direct diagnoses.

State decision release-ready: `ready` means every requirement is verified. It does not mean merged or deployed. Describe `feedback` as a record `engage` can route, with no collector. State that a git merge is not integration success.

Add `tests/test_readme_lifecycle.py` that reads `README.md` and asserts the two modes, the verify/assess split, the escalation ladder, and that `ready` is not deployed.

Document only behavior the skills already state. Do not edit the skills.
