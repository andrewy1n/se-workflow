## Orientation

Inline task in phase-selector wave 1. Implement in the worktree at /home/andre/se-workflow--phase-selector. Code files: dashboard/model.py, tests/test_dashboard_model.py. This is the first implementation task; model helpers are used by later tasks.

## Quoted requirements

R1: Each effort that has phase records opens on its default phase: the in-progress phase with the most recent activity; if none is in progress, the lowest-ordinal planned phase; if none, All phases.
R7: The selection follows the default (R1) until the user selects a different phase; it then stays pinned across refreshes. Selecting the phase that is the current default resumes following. A pinned phase that no longer exists falls back to following. Each effort keeps its own selection across effort switches in a session.
R10: Activity merges consecutive items of the same kind and outcome into one line naming their subjects, for example `R1 R2 R3 R4 R7 insufficient → verify` or `4 checks passed: a, b, …`, clipped to the pane width. Failed items keep the error colour.
R13: An effort with no phase records shows no selector and no wave strip, and its table renders as before.

## Quoted design invariants and assumptions

The snapshot model stays independent of the selection: selection is UI state and filters a loaded EffortView.
Needs you and Activity content do not depend on the selection.
Status values and task order are unchanged.
Activity items exist for running phases often enough to rank them; a phase with none ranks by ordinal.

## Quoted named decisions

selection-follow: The selection follows the current phase until the user selects another; it then stays pinned. Selecting the current phase again resumes following.
parallel-phase-default: When several phases are in progress, the default is the one with the most recent activity.
activity-merge: Activity merges consecutive items of the same kind and outcome into one line naming their subjects.
