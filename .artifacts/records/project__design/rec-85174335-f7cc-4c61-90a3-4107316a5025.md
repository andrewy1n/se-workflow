## Architecture

Add `project:backlog-item` beside `project:feedback` in the bundled contract. Pattern is `current-status`: lifecycle active/superseded so status can change via supersede. Payload requires `effort` and `status` (`open` | `promoted` | `dismissed`); `source` and `phase` are optional (`phase` set when promoted). The item body holds the parked description.

Status changes use `supersede` of the active record. Open items are lifecycle `active` and `payload.status` `open`.

`project:feedback` stays an observation and is untouched.

Handoff gains a role for open backlog items, grouped by `effort`, selecting `lifecycle_state` active and `payload.status` equals `open`.

The dashboard effort pane adds a **Backlog** panel (separate from Needs you, Tasks, and Journal). `EffortView` carries open backlog items for that effort. Detail view supports promote and dismiss: both call adaptive-artifacts CLI supersede; promote also copies an agent prompt naming the effort and starting discuss (or incidental). Skills document create/list/promote for agents; dashboard is the human surface for the same open set.

## Interfaces

Create / list / supersede CLI shapes unchanged from the prior design (create open; list status=open; supersede promoted|dismissed).

Dashboard:

- Model: load open `project:backlog-item` records per effort into the snapshot (status equals open).
- UI: Backlog panel on the effort pane; open on focus or a dedicated key consistent with existing panels.
- Promote: `supersede` status `promoted`, copy prompt to continue in chat with discuss for that effort/item.
- Dismiss: `supersede` status `dismissed`; refuse non-backlog kinds if shared helpers are used.
- Same store targeting and binary as `dashboard/dismiss.py` / Needs you.

Engage: list open backlog after focus; offer capture; on promote route to discuss/new phase or incidental. Do not scrape GitHub. Do not create feedback for parking.

## Decisions

- backlog-vs-feedback: new `backlog-item`; keep `feedback`
- backlog-effort-scope: `effort` required
- backlog-promote: close via supersede and route to discuss/new phase or incidental work-item
- backlog-capture: parent/session CLI capture; no collector
- backlog-item-pattern: `current-status` with supersede
- backlog-dashboard-surface: separate Backlog panel
- backlog-dashboard-actions: CLI supersede + agent prompt on promote

## Invariants

- Feedback never stores deferred backlog.
- Structured promote never skips discuss for a new phase.
- Every backlog-item has an effort subject that names a goal area.
- Only `status=open` active items appear in handoff and the Backlog panel.
- Needs you never lists backlog items.

## Assumptions

- `current-status` supersede works like assessment and goals.
- Needs you prompt-copy and CLI dismiss patterns extend cleanly to backlog actions.
- No adaptive-artifacts runtime change is required.

## Tradeoffs

- Separate panel vs Needs you: clearer urgency model; more UI and tests.
- Prompt-copy promote vs in-process discuss: keeps single-writer skills; one extra paste step.
- Extra record type instead of widening feedback: clearer engage rules.

## Risks

- Handoff/dashboard selection must use `equals open` so missing status never looks open.
- Sharing dismiss helpers with Needs you could accidentally allow backlog in HUMAN_DISMISSIBLE or the reverse — keep kinds and actions explicit.
- Shell wrappers redirecting `--store` can hide writes; dashboard must keep using Target.cli_args().
