## Architecture

`dashboard/model.py` loads the evidence types with the other `list` calls in `load_snapshot`: specification, design, assessment, integration-report, release, and acceptance. Each type that fails to list is treated as empty, so an older contract still loads. Per effort it builds a `PhaseEvidence` for each phase that has a specification: requirement rows, the current stage, the latest integration-report, and release ready. It also adds the Needs-you and activity items. A new `load_requirement_detail` does the per-requirement queries, including superseded assessments for the history, only when that screen opens.

A new `dashboard/requirement_detail.py` holds `RequirementDetailScreen`, in the same way `task_detail.py` holds the task screen. `PhaseDetailScreen` in `app.py` gains the stage strip, specification summary, decisions, integration result, and a requirement list. `TaskDetailScreen` gains requirement and decision links. `tasks.py` adds the tally to phase section rows. The stepper adds the stage word.

Stage derivation for a structured phase, first match wins: a latest release `ready` gives release. Otherwise, if any latest assessment is not `verified`, the earliest `next` among them in loop order. If every requirement is verified, release. Otherwise by records present: no design gives design, no work-items gives plan, any work-item not done gives execute, a wave with more than one task and no passing integration-report gives integrate, an acceptance with a requirement and no check-run gives verify, else assess.

## Interfaces

- `RequirementRow(phase, id, text, status, next, latest_check, tasks)`, where status is an assessment status or `unassessed`.
- `PhaseEvidence(phase, weight, requirements, stage, integration, release_ready, decisions, non_goals)`.
- `PhaseRow` gains `evidence: PhaseEvidence | None`. `None` means a simple phase, and every renderer branches on it.
- `EffortView.release_ready: bool`.
- `NeedsYouItem` kinds `loop-route` and `integration`, carrying the phase and requirement id.
- `ActivityItem` kinds `assessment`, `integration`, `release`.
- `load_requirement_detail(target, effort, phase, requirement) -> RequirementDetail`.
- Link keys `req:<phase>:<id>` and `decision:<subject>`, next to the existing `task:` and phase prefixes.

## Decisions

evidence-under-phase, evidence-view-scope, unassessed-requirement-status, loop-needs-you-triggers, release-ready-badge, stage-strip-placement.

## Invariants

Status comes only from the latest assessment for that phase and id. Requirement identity is phase plus id. A phase with no specification takes every existing code path unchanged. The dashboard stays read-only.

## Assumptions

Requirement text parses from `R<n>: text` lines under `## Requirements`. Comma-separated `requirements` and `decisions` payloads split on commas with whitespace trimmed. A check-run's phase comes from its acceptance through `criterion_id`. `list --state superseded` returns earlier assessments.

## Tradeoffs

Phase-scoped requirements give no cross-phase list. Loading evidence in the snapshot adds about six `list` calls to each refresh. They run in the existing thread pool, while the history loads only on demand. Dimming the check result for unassessed rows keeps the evidence visible without letting a check-run claim a status.

## Risks

`app.py` is already over 1000 lines. The requirement screen goes in its own module, and phase detail additions should stay small. The 60 column layout of phase detail and Needs-you lines needs pilot coverage. Refresh time could grow; the model tests should keep the seeded snapshot fast. With no real structured data yet, the seeded store must match what the skills actually write.
