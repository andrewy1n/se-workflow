## Architecture

A new pure module `dashboard/gates.py` owns the gate vocabulary: `action_label(item)`, `prompt(item, effort)`, and `next_step(view, landing)`. `NEEDS_LABEL` in `app.py` is replaced by `action_label`, so the list row, the detail chips, and the footer agree (R1). `action_label` recognizes `plan-review:` scopes and looks the slug up in `view.phases` for the title (R2).

`dashboard/landing.py` reads git state. `phase_landing(root, phase_body, subject)` returns `Landing(branch, exists, ahead, merged)` or `None` when the body has no `## Landing` heading. It runs `git rev-parse --verify --quiet refs/heads/<branch>`, `git rev-list --count main..<branch>`, and `git merge-base --is-ancestor <branch> main`, each with a 2 s timeout; any failure returns `None` (R5, R10, R11). The model already lists phases; `load_snapshot` keeps each phase body on `PhaseRow.body` so landing needs no extra query. The app computes landing in a worker after each snapshot load and caches it by the output of `git rev-parse main <branches>`, so the 2 s refresh does not run git when nothing moved.

`model.needs_you_items` gains a `landing` argument; a done phase whose landing exists and is not merged yields a `merge-branch` item placed after `integration` in `NEEDS_ORDER` (R6). Because the snapshot builder stays git-free, the app merges landing items into `view.needs_you` after the worker returns; `dashboard-status` and the tmux segment call the same merge so their counts match.

Quiet: `TaskRow` gains `last_record_at: datetime | None`, the latest of its assignment, amendment, execution report, and check-run `recorded_at`, set where `running_since` is set today. `gates.is_quiet(task, now)` compares `now - last_record_at` with `2 * estimate_minutes` or 60 minutes (R7). `tasks.status_label` and `selection.wave_strip` use it.

`EffortPane` gets a `#next-step` Static after `#goal`, filled from `next_step` plus the position text (R4). `c` dispatches on focus: Needs you copies `prompt(item, effort)`, the task table copies the slug (R3).

Alerts: `DashboardApp` keeps `seen_needs: set[str]` of item ids. After each reload, ids not in the set (skipped on the first load) trigger `self.bell()` and, when `$TMUX` is set, `tmux display-message -d 4000 "<effort>: <label> <subject>"` (R9).

The status-right segment: `dashboard/bin/dashboard-status --tmux <dir>` prints `⚑ <n>` or nothing. `se-workflow.tmux` reads `@dashboard-status-right` (default `on`) and appends `#(cd '#{pane_current_path}' && <launcher dir>/dashboard-status --tmux .)` to `status-right` once, checking for an existing copy so reloading tmux.conf does not duplicate it (R8).

## Interfaces

- `action_label(item: NeedsYouItem, view: EffortView) -> str`
- `prompt(item: NeedsYouItem, view: EffortView) -> str`
- `next_step(view: EffortView, landing: dict[str, Landing]) -> str`
- `Landing(branch: str, exists: bool, ahead: int, merged: bool)`
- `phase_landing(root: Path, body: str, subject: str) -> Landing | None`
- `PhaseRow.body: str`; `TaskRow.last_record_at: datetime | None`
- `NeedsYouItem` kind `merge-branch` with `phase` set
- `is_quiet(task: TaskRow, now: datetime) -> bool`
- `dashboard-status --tmux DIR`
- tmux option `@dashboard-status-right` (`on` | `off`)

## Decisions

needs-you-copy-prompt, next-step-source, landing-display, quiet-threshold, needs-you-alerts.

## Invariants

`load_snapshot` stays free of git calls; landing is merged in by the app and the status scripts. Every git command is read-only. Item ids for alerts are record ids, or `merge:<phase>` for branch items, so a refresh does not re-alert.

## Assumptions

Phase bodies name the branch as `phase/<phase-slug>`; when the Landing text names another branch in backticks after `branch`, that name is used. The default branch is `main`, as Landing states.

## Tradeoffs

Merging landing items outside the model means two places build Needs you (the model and the landing merge), in exchange for a model that never shells out to git. The next-step rules are a fixed priority list; an effort with several gates shows only the first, and Needs you lists the rest.

## Risks

Appending to a user's `status-right` can collide with their own configuration; the guard against duplicates and the `off` option limit that. tmux format expansion inside `#()` varies across old tmux versions; the tmux test pins behaviour on the installed version. Bells from a side pane may be noisy in a busy phase; alerts fire only for new ids, never on refresh.
