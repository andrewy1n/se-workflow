## Architecture

A new `dashboard/journal.py` holds the model function and the screen. `load_journal(target, effort)` lists the five types for the effort with `--full` (each type that fails to list is treated as empty, R9). It maps task-scoped subjects to phases through the effort's work-items, and turns each record into a `JournalItem` with its phase, time, one-line text, and open flag (R2, R3, R4). The open rules reuse the Needs you predicates for questions and findings from `model.py`, so the two never disagree.

`JournalScreen(target, effort, phase)` is a pushed screen with a `DataTable` in row cursor mode, a separator row between open and other items, and a `FilterInput`, reusing the task-table filter widget (R1, R4, R6). Enter pushes `RecordDetailScreen`, a generic screen that renders type, subject, payload fields, and body as Markdown (R5). The Needs you detail screen is built the same way and can move onto it later. `o` reuses `pager_command` from spec-view.

Kind panel: `EffortView` gains `kind` from the goal payload, and `load_snapshot` attaches `journal_open: list[JournalItem]` for repair and evaluate efforts only, so delivery snapshots do no extra listing. `EffortPane` adds a `JournalPanel(OptionList)` before `#tasks`, filtered to the selected phase through `selection.scoped`. It is hidden when the panel is empty or the kind is deliver or incidental (R7).

Agent work: `task_detail.load_task_detail` already lists assignments and reports for the timeline. It now keeps their bodies and lists amendments by `payload.assignment`. `AgentWork` groups them per assignment, newest first. `TaskDetailScreen` adds an `AgentWorkPanel` of `CollapsibleBlock` widgets. Each holds the full text, shows the first 8 lines with `+n lines`, toggles on Enter, and answers `pager_text()` for `o`. Earlier assignments appear as a list whose Enter swaps the blocks shown (R8).

## Interfaces

- `JournalItem(id, record_type, subject, phase: str | None, recorded_at, text, open: bool, task_id: str)`
- `load_journal(target, effort: str) -> list[JournalItem]`
- `journal_scope(items, phase: str | None) -> list[JournalItem]` (phase items plus effort-only open questions)
- `ordered(items) -> tuple[list[JournalItem], list[JournalItem]]` (open, rest)
- `JournalScreen(target, effort: str, phase: str | None)`; keys `a`, `/`, `enter`, `o`, `escape`
- `RecordDetailScreen(target, record_id: str)`
- `EffortView.kind: str`, `EffortView.journal_open: list[JournalItem]`
- `AgentWork(assignment, amendments, report)`; `TaskDetail.agent_work: list[AgentWork]`
- `CollapsibleBlock(title: str, text: str, lines: int = 8)`

## Decisions

journal-screen, journal-order, journal-types, kind-journal-panel, task-agent-work.

## Invariants

Only repair and evaluate efforts pay for journal loading on the main snapshot. The journal screen loads on open and reloads on store change like the other detail screens. Record text is shown as stored.

## Assumptions

Task-scoped journal records use the task slug as `subject` and carry `payload.effort`, as kinds-and-focus.md requires. Assignment bodies have an `## Orientation` section and amendments a `## Correction` section, as the contract requires.

## Tradeoffs

The kind panel adds up to 6 lines above the task table for repair and evaluate efforts, which pushes the table down in a short popup. Collapsing agent text to 8 lines hides most of a report until expanded, in exchange for a task detail that stays scannable.

## Risks

Older records without `payload.effort` fall back to the single-goal rule in kinds-and-focus.md; with several goals they are left out, and a test pins that. Large execution reports (verbatim bodies) can be long; the blocks render lazily on expand so the task detail opens quickly.
