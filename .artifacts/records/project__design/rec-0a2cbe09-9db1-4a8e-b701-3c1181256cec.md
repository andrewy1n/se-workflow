## Architecture

Verification time is capped by what the instructions tell the executor to run, and by refusing edits during verification.

`plan-phase` writes the verification task's acceptances from the phase exit criteria only. One of them is the integration check through the real entry point. A `verify_command` that runs the whole `tests` tree, or `tests/test_dashboard_app.py` without a `-k` filter for this phase, is not a legal verification acceptance.

`execute-phase` dispatches that task with those commands. The executor returns the evidence block. On fail it returns fail and does not edit the worktree.

`verify-work` records the failing check-run, writes the assessment with `next` `execute`, and leaves the work-item `in_progress`. It does not launch a repair and it does not run a suite the acceptance does not name.

`AGENTS.md` and `CLAUDE.md` tell a task to run the affected files and that task's `verify_command`. They drop the instruction to run the full suite before close.

Planned acceptances on `verify-spec-view`, `verify-evidence-matrix`, and `verify-journal-view` whose command is the full suite are superseded with the phase-scoped command before those tasks dispatch. Done verification records stay as history.

## Interfaces

`skills/plan-phase/SKILL.md`, the verification-task step.

`skills/execute-phase/SKILL.md`, the verification dispatch and the fail return.

`skills/verify-work/SKILL.md`, the fail path and the assessment row `next` `execute`.

`AGENTS.md` and `CLAUDE.md`, section Testing.

Active acceptances for `verify-spec-view`, `verify-evidence-matrix`, and `verify-journal-view`.

`tests/test_verify_budget.py` locks the instruction text. `tests/test_skill_contract_consistency.py` still allows every CLI invocation those skills document.

## Decisions

`phase-checks-only`: verification runs the phase's checks, and task close does not add the full suite.

`verify-stop`: a failing verification check routes to execute, and the verification task does not edit the tree.

## Invariants

The phase still has one verification task that depends on the other work-items.

One acceptance is still an integration check through the real entry point.

A failed check caused by the task's code still uses assessment `next` `execute`.

The parent session remains the only store writer.

## Assumptions

Phase-scoped commands are short enough that the verification task finishes within 10 minutes, including executor time, because the executor no longer edits the tree.

Regressions outside the named tests are outside this loop.

## Tradeoffs

The loop no longer catches a break in a screen the phase did not touch. That coverage was the reason to keep one full suite.

A small fix that verification can already see waits for another execute dispatch.

## Risks

An exit criterion can still name a huge file and miss the budget. `plan-phase` has to reject a whole-tree command and an unfiltered `tests/test_dashboard_app.py` command.

Nothing in the contract engine stops an executor from running the suite anyway. The instruction text is the control.

Model time can still exceed 10 minutes if the executor wanders. The short command and the no-edit rule are what keep the span inside the budget.
