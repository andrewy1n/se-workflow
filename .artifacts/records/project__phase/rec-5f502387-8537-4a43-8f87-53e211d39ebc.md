## Problem

evidence-loop added specification, design, integration-report, assessment, and release records, and trace fields on work-items, acceptances, and check-runs. The dashboard reads none of them. For a structured phase you cannot see which requirements are verified, why a task exists, where an assessment routed the loop, whether integration failed, or whether the phase is release ready. The task table answers "what is running" but not "is it proven".

## Approach

Decisions: evidence-under-phase, evidence-view-scope, unassessed-requirement-status, loop-needs-you-triggers, release-ready-badge, stage-strip-placement. Run as structured work: specification `evidence-view`, design `evidence-view`.

Requirements live under their phase, because requirement ids are unique only within a phase. A structured phase header in the task table carries `R n/m verified`. Phase detail lists each requirement with its status from the latest assessment (or `unassessed` with the latest check result dimmed), next stage, and traced task count. Enter opens a requirement detail screen: requirement text, decisions, traced tasks and acceptances, latest check-runs with evidence kind, and the assessment history oldest first. Task detail links to its requirements and decisions.

Phase detail shows the full stage strip, the specification summary, design decisions, and the latest integration-report. The stepper shows only the current stage word. Needs you gains latest assessments that route to specify, design, or plan, are blocked, or have low confidence, and failed or blocked integration-reports. A ready release shows a Release ready badge; the derived "finished" rule is unchanged. Activity lists assessments, integration-reports, and releases.

Simple phases and incidental work render exactly as before.

Size: more than one sitting. Human stops: none beyond plan review.

Waves:
1. `evidence-model` (subagent) owns `dashboard/model.py` and `tests/test_dashboard_model.py`. Every later task reads the model and does not edit it.
2. `requirement-screen` and `evidence-surfaces` (subagent, parallel). `requirement-screen` owns the new `dashboard/requirement_detail.py` and `tests/test_dashboard_requirement.py`. `evidence-surfaces` owns `dashboard/app.py`, `dashboard/tasks.py`, and `tests/test_dashboard_app.py`. The shared interface is `RequirementDetailScreen(target, effort, phase, requirement)` in `dashboard/requirement_detail.py`. `evidence-surfaces` does not import it; wave 3 wires it.
3. `requirement-links` (inline) wires enter from phase detail, Needs you, and task detail into the requirement screen. It edits `dashboard/app.py`, `dashboard/task_detail.py`, and `tests/test_dashboard_app.py` after wave 2 has merged.
4. `verify-evidence-view` (subagent) adds the tmux test in `tests/test_e2e_dashboard.py`, the README section, and runs the full suite.

Collision notes: wave 2 shares no written file. Both wave 2 tasks read the frozen `model.py` interfaces from wave 1.
