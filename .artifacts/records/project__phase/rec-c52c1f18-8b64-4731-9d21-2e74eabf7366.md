## Problem

The workflow stops at fixed human gates: plan review, manual sign-off, needs-human findings, upstream routes, failed integration, and landing a phase branch. The dashboard shows some of these in Needs you with noun labels (`blocking`, `unsigned`, `question`) that do not say what to do, and plan review reads as `blocking plan-review:<phase>`. Landing state is not shown at all. Nothing says what happens next, a running task whose agent died looks the same as one that is working, and nothing tells the user a new item appeared while the popup is closed. The dashboard is read-only, so it cannot act on a gate itself.

## Approach

Decisions: needs-you-copy-prompt, next-step-source, landing-display, quiet-threshold, needs-you-alerts. Run as structured work: specification `human-gates`, design `human-gates`.

Needs you rows lead with an action verb, and `c` copies a ready agent prompt for the item. A next-step line under the goal is derived from state and names the skill to run, followed by the position text. The selected phase line shows its Landing branch, commits ahead of `main`, and merged state from read-only git commands, and a done phase with an unmerged branch becomes a Merge branch item. A running task with no new record for twice its estimate, or 60 minutes without one, is flagged quiet on its row and in the wave strip. A tmux status-right segment shows the needs-you count, and the running dashboard sends a tmux message and bell when a new item appears.

This phase edits the dashboard and `se-workflow.tmux`, and does not change `contract/project-design.json` or `~/adaptive-artifacts`. It starts after `phase-selector` is on main: it adds to the selector line and wave strip that phase builds. Quiet thresholds use the `estimate_minutes` that `estimate-view` loads.

Tasks (all `executor: subagent`):

1. `gates-vocab` — add `dashboard/gates.py` with `action_label`, `prompt`, `next_step`, and `is_quiet`. Cover with `tests/test_dashboard_model.py` (`-k gates`).
2. `gates-landing` — add `dashboard/landing.py` with `phase_landing` against a scratch git repo. Cover with `tests/test_dashboard_gates.py`.
3. `gates-model` — wire `PhaseRow.body`, `TaskRow.last_record_at`, merge-branch Needs you items, and quiet into status/wave strip. Depends on vocab and landing.
4. `gates-ui` — next-step line, `c` copies prompt, alerts/bell with stubbed tmux. Depends on model. Cover with `tests/test_dashboard_app.py`.
5. `gates-status` — `dashboard-status --tmux` and `se-workflow.tmux` status-right segment. Depends on model. Cover with a `-m tmux` test.
6. `verify-human-gates` — integration through `dashboard/bin/dashboard --once` plus the gated suites.

Collision notes: `dashboard/model.py`, `dashboard/tasks.py`, and `dashboard/selection.py` belong to `gates-model` only. `dashboard/app.py` belongs to `gates-ui` only. `gates-vocab` and `gates-landing` own new modules and must not edit app. Status scripts and `se-workflow.tmux` belong to `gates-status`. Shared fixtures for seeded stores and scratch git live under the gates test files.

Size: more than one sitting. Human stops: plan review; do not execute until the remaining UX phases (`spec-view`, `evidence-matrix`, `journal-view`) are also planned (constraint `dashboard-ux-plan-before-execute`); then landing after verification.

## Exit criteria

- Verbs, plan-review recognition, prompt text, next-step rules, landing state, the Merge branch item, and the quiet rule hold against seeded stores and a scratch git repo (`tests/test_dashboard_model.py`, `tests/test_dashboard_gates.py`).
- `c` copies the prompt and new items trigger the message and bell in a Textual pilot with tmux calls stubbed (`tests/test_dashboard_app.py`).
- The status-right segment appears in a real tmux server (`-m tmux` test).
- The full suite passes.
