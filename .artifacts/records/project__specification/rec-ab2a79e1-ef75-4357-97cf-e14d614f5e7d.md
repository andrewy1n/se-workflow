## Requirements

R1: The phase screen replaces phase detail and has tabs Overview, Spec, Design, Decisions, Evidence, Tasks. A phase with no specification, or whose contract lacks the specification type, shows Overview, Spec, Decisions, and Tasks. `left` and `right` move between tabs; `p`, `s`, `d`, `e`, and `t` jump to Overview, Spec, Decisions, Evidence, and Tasks.
R2: On the main screen `p` opens the phase screen at Overview, `s` at Spec, and `e` at Evidence, for the selected phase; on All phases, for the cursor row's phase. On a simple phase `e` opens Overview.
R3: Overview shows the title, chips, stage strip, progress, the next-step line, landing state, and the latest integration result; for a structured phase it also shows the phase body.
R4: Spec, for a structured phase, renders the full specification body as Markdown with every section, and lists each requirement as a selectable row `R<n> <text>`; Enter opens its requirement detail. Phase constraints follow the specification.
R5: Spec, for a simple phase, renders the phase body (Problem, Approach, Exit criteria, Landing) and the phase constraints.
R6: Design renders the full design body as Markdown with every section.
R7: Decisions lists the phase's active decisions as rows with subject and choice; Enter expands a row to alternatives, rationale, and counter-argument. `a` toggles the whole effort, grouped under phase titles in ordinal order. `h` toggles superseded decisions, each shown dimmed under its successor with `supersedes` and its own choice.
R8: Evidence shows the requirement list and integration result phase detail shows today, with the same Enter behaviour.
R9: Tasks lists the phase's tasks as phase detail does today; Enter opens the task detail.
R10: `[` and `]` on the phase screen move to the previous and next phase in ordinal order and keep the current tab when the new phase has it, else Overview. They do not change the main screen's selection.
R11: `o` writes the current tab's full text as Markdown to a temporary file outside the store, suspends the app, opens it with `glow -p` when `glow` is on PATH, else `$PAGER`, else `less`, and deletes the file when the pager exits.
R12: Esc from a requirement, task, or decision opened from the phase screen returns to the phase screen on the same tab and row. Esc on the phase screen returns to the main screen.
R13: The phase screen reloads on store change, as phase detail does today, keeping the tab, toggles, and scroll position.

## Acceptance criteria

R1, R5, R7 data (phase and effort scope, superseded chains), and R13 reload: model tests in `tests/test_dashboard_model.py` against seeded stores, selected with `-k phase_screen`.
R1 to R4, R6 to R10, R12 on screen: Textual pilot tests in `tests/test_dashboard_phase_screen.py`.
R11: a pilot test with `glow` absent and `$PAGER` set to a stub script that records the file it received and its text; the file is gone afterwards.

## Constraints

The dashboard stays read-only (constraint dashboard-read-only); the pager temp file is outside `.artifacts`. No change to `contract/project-design.json` or `~/adaptive-artifacts`. Nothing executes until all five UX phases are discussed (constraint dashboard-ux-plan-before-execute).

## Non-goals

The requirements matrix (evidence-matrix). The journal and kind-based default (journal-view). Editing any record. Rendering derived view files.

## Invariants

Every record section shown on a tab is the record's own text, not a summary. The tab set depends only on whether the phase has a specification. Opening the phase screen never changes the main screen's selection.

## Assumptions

Superseded decisions are reachable through the CLI with their successor relation (`list --state superseded` and the record's supersede link). `glow -p` pages its output and exits on `q`.
