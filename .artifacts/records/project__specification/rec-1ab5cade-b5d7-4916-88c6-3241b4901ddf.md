## Requirements

R1: A verification task runs that phase's integration check through the real entry point, and the tests that phase's exit criteria name.

R2: A verification `verify_command` does not run the whole `tests` tree. It does not run `tests/test_dashboard_app.py` or another pre-existing pilot file unless a `-k` filter limits it to the tests this phase added.

R3: Closing a task runs that task's `verify_command`. `AGENTS.md` and `CLAUDE.md` do not tell the agent to run the full suite before close.

R4: When a verification check fails, the executor returns fail and does not edit the tree. The work-item stays `in_progress`. The assessment for that requirement uses `next` `execute`.

R5: Planned verification tasks `verify-spec-view`, `verify-evidence-matrix`, and `verify-journal-view` no longer carry a full-suite acceptance when they dispatch.

## Acceptance criteria

`tests/test_verify_budget.py` fails if `skills/plan-phase/SKILL.md`, `skills/execute-phase/SKILL.md`, `skills/verify-work/SKILL.md`, `AGENTS.md`, or `CLAUDE.md` instructs a verification task or a task close to run the full suite (`pytest tests` with no file and no `-k`, or the `-n 4 -m "not tmux"` command chained with `-m tmux`).

That test fails if `skills/execute-phase/SKILL.md` omits the instruction that a verification executor returns fail and does not edit the tree.

`python3 -m pytest tests/test_skill_contract_consistency.py -q` passes.

After the planned acceptances are superseded, `verify-spec-view`, `verify-evidence-matrix`, and `verify-journal-view` have no active acceptance whose `verify_command` is the full suite.

## Constraints

A deliver or repair phase still ends with one verification task that `depends_on` the other work-items in the phase.

One verification acceptance is still an integration check through the real entry point.

A failed check whose cause is the task's code still assesses as `next` `execute`.

The parent session remains the only writer of the store.

The README may still document the full suite as a command a person can run.

## Non-goals

Speeding up `tests/test_dashboard_app.py`.

Adding CI.

Rewriting verification tasks that are already `done`.

Changing the adaptive-artifacts runtime.

## Invariants

The phase gate still requires the verification task to be `done` and each remaining acceptance's latest check-run to pass.

Implementation tasks still follow red-first for their own `verify_command`.

A tmux test that a phase names still runs serially.

## Assumptions

A command limited to the phase's tests finishes fast enough that the verification task's in-progress to done span stays within 10 minutes.

A regression outside those tests is outside this loop.
