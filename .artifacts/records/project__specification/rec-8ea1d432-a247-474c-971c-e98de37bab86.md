## Requirements

R1: The bundled contract defines `project:backlog-item` so deferred work can be created and listed in the store.

R2: `project:feedback` semantics stay unchanged: engage routes it into discuss; nothing collects it; agents do not create it as a standing backlog.

R3: A backlog item requires `payload.effort` naming a live or reopenable goal subject; `source` (and an external link in the body when useful) is optional.

R4: Status covers open work and the terminal outcomes promoted and dismissed, using current-status supersede.

R5: Promotion closes or supersedes the open item and starts the normal loop for that effort (usually discuss with a new phase; incidental-sized items may become a single incidental work-item). Skills document capture and promote. This phase does not auto-scrape GitHub issues into the store.

R6: The terminal dashboard shows open backlog items for the selected effort in a separate Backlog panel (not Needs you). Promote and dismiss run through the adaptive-artifacts CLI (supersede); promote also copies an agent prompt to continue in chat. Handoff still lists open items.

## Acceptance criteria

- The bundled contract resolves `project:backlog-item` and still resolves `project:feedback`.
- Documented CLI invocations for backlog-item in skills pass `tests/test_skill_contract_consistency.py`.
- README and engage distinguish feedback (route now) from backlog-item (park and later promote).
- A seeded store can create a backlog-item, list open items for an effort, and promote or dismiss without treating the record as feedback.
- Dashboard model and UI tests show open backlog items on the Backlog panel for an effort, hide promoted/dismissed items, and exercise promote/dismiss via the CLI path (pilots through the app entry point where UI is claimed).

## Constraints

- Contract changes stay in se-workflow's `contract/project-design.json`; do not patch the adaptive-artifacts runtime for this phase.
- `payload.effort` is required; repo-wide unassigned backlog items are out of scope.
- Parent session writes records; subagents do not write the store.
- Dashboard promote/dismiss must not invent a second clear model next to Needs you dismiss — same CLI binary and store targeting.

## Non-goals

- GitHub two-way sync or scraping issues into the store
- Widening or replacing `project:feedback`
- Repo-wide items without an effort
- Folding backlog into the Needs you list
- Starting discuss or plan-phase inside the Textual process

## Invariants

- Feedback never becomes the backlog store.
- Promoting structured work never bypasses discuss for a new phase.
- Open backlog items remain queryable and visible in handoff and the dashboard Backlog panel until promoted or dismissed.
- Needs you stays limited to human gates; backlog stays inventory.

## Assumptions

- Live goals already name product areas; parking work always attaches to one of those subjects (or a reopenable closed goal).
- Users (or the parent session on their instruction) create backlog items explicitly; no background collector is required.
- Existing Needs you prompt-copy and CLI dismiss patterns are the template for backlog actions.
