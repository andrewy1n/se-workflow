## Requirements

R1: A structured phase's header row in the task table shows `R n/m verified`, where m is the number of ids in its specification and n is how many have a latest assessment of `verified`.
R2: Phase detail of a structured phase lists each requirement with its id, status, next stage, and the number of work-items whose `requirements` include it. Status is the latest assessment's status, or `unassessed` with the latest check-run result for that requirement shown dimmed.
R3: Enter on a requirement opens a requirement detail screen showing the requirement text from the specification, the decisions of the tasks traced to it, the traced tasks and acceptances, the latest check-run per acceptance with its evidence kind, and every assessment for it oldest first with status, level, next, and confidence. Enter on a traced task opens its task detail; esc returns one screen at a time.
R4: Task detail lists the task's requirements and decisions. Enter on a requirement opens its requirement detail.
R5: Phase detail of a structured phase shows the stage strip specify, design, plan, execute, integrate, verify, assess, release with the current stage marked, the specification weight and non-goals, the design decisions, and the latest integration-report result with its conflicts. The stepper's current phase shows the current stage word.
R6: Needs you lists each requirement whose latest assessment has `next` of specify, design, or plan, a status of `blocked`, or `confidence` `low`, and each phase whose latest integration-report is `fail` or `blocked`. Enter on an assessment item opens the requirement detail; enter on an integration item opens the Needs-you detail.
R7: A latest release with state `ready` shows a Release ready badge on the effort and on its phase. The derived "finished" rule does not change.
R8: Activity lists assessments (requirement, status, next, marked when the route goes upstream or the level escalates), integration-reports, and releases. Failed and blocked ones use the error colour.
R9: A phase with no specification, and incidental work, render exactly as before: no tally, strip, stage word, badge, or new Needs-you item.
R10: A store whose contract lacks any evidence-loop type loads with no error and renders as before.

## Acceptance criteria

R1, R2, R7, R9, R10 and the R6 and R8 item lists: model tests in `tests/test_dashboard_model.py` against seeded stores, selected with `-k evidence`.
R1 to R9 on screen: pilot tests in `tests/test_dashboard_app.py` at 60 and 120 columns, selected with `-k evidence`.
End to end: a tmux popup test through the real entry point, and the full suite passes.

## Constraints

The dashboard never writes to the store. The snapshot comes from `adaptive-artifacts list` JSON (decision dashboard-data-source). Detail views are pushed full screens that esc closes (decision task-detail-presentation). No change to `~/adaptive-artifacts`. Tests do not hardcode today's record type list as frozen.

## Non-goals

A node-and-edge graph of the whole effort. A separate Requirements screen or table mode. Showing feedback records. Writing or editing records from the dashboard. Changing how "finished" is derived.

## Invariants

The latest assessment is the only source of a requirement's status; a check-run never sets it. A requirement is identified by phase plus id. Simple phases render identically before and after.

## Assumptions

The specification's Requirements section has one `R<n>: text` line per id, as `discuss` writes it; a missing line shows the id without text. `list --state superseded` returns earlier assessments for the history. This repo's store has no structured-phase data yet, so tests use seeded stores and this phase produces the first real data.
